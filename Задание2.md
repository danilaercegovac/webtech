## Образование
АПИ - контракт коммуникации с системой. Разработчикам систем необходимо предоставлять потребителям системы информацию об АПИ - появилась задача на документацию АПИ. 

Сначала все делали по-своему, но далее выявили определённый стандарт - OpenAPI. Им начали описывать АПИ до начала разработки. Существует множество интересной исторической информации о стандарте.

Свойство стандарта - наличие структуры. Доступные языки стандарта JSON и YAML. Стандарт, его структура состоит из переменных / секций и их значений. Переменные имеют строгий порядок и характеристику обязательности:
1. openapi - первая обязательная переменная, номер версии спецификации OpenAPI.
   1. Если не указать, то валидатор (например, Swagger Editor) покажет ошибку, интерактивная документация (например, Swagger UI) не создастся, генератор кода даст ошибку (например, OpenAPI Generator, Swagger Codegen).
   2. Если указать одну версию, а в описании использовать синтаксис стандарта предыдущих или последующих версий, то инструменты (валидаторы, генераторы кода, документации, генераторы кода) проигнорируют синтаксис отличной версии или вернут ошибку.
2. info - вторая обязательная переменная, справочная информация о документе. Имеет:
   1. Обязательные переменные: title (заголовок) и version (версия документа)
   2. Необязательные переменные: description, termsOfService, contact, license
3. servers - третья необязательная переменная, список серверов-адресатов АПИ-запросов. Если не указано, то значит адрес сервера не определён. Состоит из:
   1. url - обязательная переменная, адрес сервера. Может быть множество url, например, тестовый и промышленный. Может содержать переменные в {} (например, https://{host}/v1).
   2. description - необязательная переменная, описание url.
   3. variables - описание переменных {} из url, обязательная переменная, если переменные содержаться в url. Состоит из:
      1. (Название переменной из {} url'а) - обязательная. Имеет:
         1. default - обязательная переменная, значение переменной по умолчанию
         2. enum - необязательная переменная, список допустимых значений, должен иметь значение по умолчанию. При наличии пользователь сможет отправить запрос только с значением из списка
         3. description - необязательная переменная, описание переменной

## Описание практической работы
Решил использовать Yandex Cloud для решения задачи: API-шлюз и Функцию.
Спецификация API-шлюза:
```
openapi: 3.0.0
info:
  title: Sample API
  version: 1.0.0
servers:
- url: https://d5djcq87ui1pjpor1bj7.bu9mdbe1.apigw.yandexcloud.net
paths:
  /:
    get:
      x-yc-apigateway-integration:
        type: dummy
        content:
          '*': Hello
        http_code: 200
        http_headers:
          Content-Type: text/plain
          Access-Control-Allow-Origin: "*"
  /login/:
    get:
      x-yc-apigateway-integration:
        type: dummy
        content:
          '*': danilaercegovac_3
        http_code: 200
        http_headers:
          Content-Type: text/plain; charset=utf-8
          Access-Control-Allow-Origin: "*"
  /sample/:
    get:
      x-yc-apigateway-integration:
        type: cloud_functions
        function_id: d4evdeajkuobqdsttas2
        tag: latest
```
### Описание особенности описания OpenAPI для API-шлюза в Yandex Cloud
После указания типа http-метода API-шлюз требует указание `x-yc-apigateway-integration`. Дело в том, что стандарт OpenAPI предусматривает структуру, описанная выше, для клиента (доступные методы, ответы, схемы, заголовки и тд), то есть то, что клиент будет получать от сервера. Так, стандарт OpenAPI служит документацией API-сервиса, по которой разработчики серверной стороны разрабатывают соответствующую backend-часть.

Но в Yandex Cloud в описании OpenAPI для API-шлюза можно декларировать поведение непосредственно серверной стороны. Стандарт OpenAPI позволяет внедрять в вендорские расширения в классическое описание через указание префикса `x-` для поля. Так, раздел `x-yc-apigateway-integration` и все под ним поля есть спецификация, разработанная Yandex Cloud и работающая исключительно в экосистеме Яндекса. Раздел `x-yc-apigateway-integration` как раз даёт инструкцию серверу, что ему сделать при получении запроса. 

Структура раздела x-yc-apigateway-integration зависит от параметра type, типа интеграции:
* dummy - Возвращает фиксированный ответ без обращения к внешним сервисам
  * http_code - код ответа
  * http_headers - заголовки
  * content - тело ответа
* cloud_functions - вызов Cloud Functions
  * function_id - Идентификатор функции (например, `d4evdeajkuobqdsttas2`)
  * tag - Тег версии функции (по умолчанию latest - последняя версия функции, могут быть пользовательские )
  * service_account_id - Сервисный аккаунт для вызова функции
* http - Перенаправляет запрос на указанный URL
  * url	- string	- URL для перенаправления (обязательный)
  * method	- enum	- HTTP-метод (если не указан — используется метод исходного запроса)
  * headers	- map[string, string | string[]]	- Заголовки, передаваемые в запросе
  * query	- map[string, string | string[]]	- Query-параметры
  * timeouts	- object	- connect и read таймауты в секундах
  * omitEmptyHeaders	- boolean	- Не передавать пустые заголовки
  * omitEmptyQueryParameters	- boolean	- Не передавать пустые query-параметры
  * service_account_id - string	- Сервисный аккаунт для авторизации
* object_storage - Делегирует обработку запроса в Object Storage для раздачи статических файлов
  * bucket	- string	- Имя бакета
  * object	- string	- Имя объекта в бакете (поддерживает подстановку параметров)
  * service_account_id	- string	- Сервисный аккаунт для доступа к бакету
* Множество остальных (serverless_containers, cloud_datasphere, cloud_datastreams, cloud_ymq, cloud_ydb)
### Результат работы
Запустил и перешёл по url успешно. Увидел Hello. Но когда пробовал переходить по путям `/login/` и `/sample/`, то встречал ошибку `/login/? not found on this server`. Связался с поддержкой. Ответили, что `API Gateway основывается на спецификации OpenAPI 3.0, где путь не должен заканчиваться слэшем`. Отредактировал пути на `/login` и `/sample` - ошибка устранилась. При переходе по пути `/sample` обнаружил ошибку `{"message":"request to function 'd4evdeajkuobqdsttas2' failed, reason: Response code 404 (Not Found)"}`. Добавил параметр service_account_id в описание cloud_functions - ошибка сохранилась. Перепроверил id функцию, всё верно. Оказалось, что последнюю версию функции надо указывать с $ -`$latest`.
