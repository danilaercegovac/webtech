### Базовая информация
#### Директивы
У языка CC существуют так называемые директивы в таком называемом препроцессоре: #include, #define, #ifdef
* #include - команда включения содержания файла в текущий файл.
Работает как вызов библиотеки. На диске у пользователя скачаны системные/дефолтные файлы , в которых содержаться объявления базовых функций типа `printf`, или пользователь имеет свои файлы, в которых им объявленные пользовательские функции.
* #define - команда "найти и заменить", находит в коде объявленные в #define имена и замечает на значения в #define
Выглядит как переменная, но переменной не является. Переменная - это конкретный объект в памяти с типом и адресом. В #define это просто текст, который заменяется. Например, можно объявить `#define PI 3.14159`, а потом в коде использовать `PI` для вычислений. В момент запуска предпроцессор заменит в коде `PI` на 3.14159. Также можно объявлять простые функции типо `SQUARE(x) ((x) * (x))`
* #ifdef, #ifndef - команды "условной компиляции", зависящий от существования/несуществования объявления "макросов" через #define
Если существует "макрос", указанный в #ifdef, то код, находящийся между #ifdef и #endif не будет скомпилирован. Аналогично с #ifndef. Используется для включения/выключения дебажных команд, вызова разных системных функций на разных операционных системах, защиты от повторного объявления функций.
#### Файлы .c, .h в языке C. Общий процесс компиляции
В языке C применяются файлы .c, .h. Они имеют разные роли в организации кода.
* .h - заголовочный файл. В нём объявляются прототипы функций (сигнатуры) (например, `int add(int a, int b);`), объявления структур и типов, макросы, include guards
* .c - файл-реализация, содержащий непосредственно логику
Получается, что при написании "модульного" .с файла, в котором, например, функции, которые планируются быть переиспользованы, то необходимо написать .h файл с таким же названием и поместить в него сигнатуру функцию, то есть только её объявление, без реализации.

Получается также, что при использовании функции из другого .c файла необходимо в нём "включить" .h файла, .c файл которого содержит функцию. 

Рассмотрим такой случай компиляции программы, в которой один .c использует функции из другого .c файла. Допустим, что файлы все .с и .h находятся в одной папке. Тогда нужно написать команду:
```
gcc main.c math_utils.c -o my_program
```
Здесь gcc - компилятор. main.c - файл, внутри которого `#include math_utils.h` и использование функции из math_utils.c. `-o my_program` - имя выходного исполняемого файла (my_program.exe).

Процесс компиляции будет выглядеть так:
1. Препроцессинг. Запускается препроцессор (часть компилятора). Выполняет директивы - подключает заголовки (#include), раскрывает макросы (#define), обрабатывает условную компиляцию (#ifdef), удаляет комментарии
Результатом являются два временных файла - main.i (это main.c со вставленным math.h, раскрытыми макросами и без комментариев), math.i
2. Компиляция. Компилятор берёт файлы .i и превращает их в объектные файлы (.o). Главный функции компиляции:
   * Проверка типов. Если, например, в math_utils.h есть функция `int sum(int a, int b);`, а в main.c в функцию попробовали указать не int, то даст ошибку
   * Генерация ассемблерный код. Результатом компиляции является .s файл, который уже ассемблер переводит в машинный код
   * Оптимизация. Компилятор перестраивает код: убирает мёртвые ветки, разворачивает циклы, инлайнит функции, перераспределяет регистры
   * «Создание дыр» (символьные ссылки). Если функция sum определена в другом файле, компилятор вставляет в ассемблерный код строку вроде call sum. На этом этапе он не знает адрес sum, поэтому оставляет символьное имя — это и есть та самая «дыра». Компилятор помечает, что позже линковщик должен подставить туда реальный адрес.
3. Ассемблирование. Ассемблер (утилита as), который запускает компилятор, берёт текстовый ассемблерный файл (.s) и переводит его в бинарный объектный код (.o). Его задачи:
   * Кодирование инструкций. Он превращает текстовые строки ассемблера (вроде call sum, mov eax, ebx) в конкретные байты машинного кода. То есть Объектный файл (.o) — это контейнер, в котором:
     * Секции с машинным кодом (.text) — там лежат байты инструкций
     * Секции данных (.data, .bss) — переменные, константы
     * Таблицы релокаций (relocation tables) — списки мест, где «дыры»
     * Таблица символов (symbol table) — имена вроде sum, main, их типы и статусы («определено/не определено»).
   * Обработка директив ассемблера. Он интерпретирует секции (.text, .data), выравнивание, метки и константы, формируя внутреннюю структуру объектного файла.
   * Сохранение символьных ссылок. Ассемблер не пытается разрешать внешние символы (вроде sum). Он просто записывает в объектный файл таблицу символов: «здесь вызывается sum, адрес пока неизвестен». Эту информацию он передаёт дальше — линковщику
4. Линковка. Линкер (утилита ld) берёт все объектные файлы (main.o, math.o) и собирает из них единый исполняемый файл. Также он подключает стандартные библиотеки (например, libc, где живёт printf). Линкер делает из .o файлов единый файл .exe. Задачи:
   * Заполнение «дыр»: Линкер видит в main.o: «Нужен адрес sum». Он заглядывает в math.o, находит там функцию sum и «вшивает» её адрес в код main.
   * Разрешение конфликтов: Если вдруг функция sum нашлась в двух разных .o файлах, линкер выдаст ошибку multiple definition.
   * Создание запускаемого файла. Когда выполняется команда `gcc main.c -o program`, то на этапе линковки компилятор GCC выполняет команду `ld crt1.o crt2.o main.o -lc -o program`, main.o - получившийся бинарник для main.c, crt1.o / crt2.o - это готовые объектные файлы из системы, в которых лежит функция _start. Функция _start - это непосредственное инструкция для ОС для запуска программы, начальная точка. Эти crt1.o crt2.o файлы предоставляет библиотека glibc (или другая C-библиотека). -lc — подключение самой библиотеки C (где живут printf, malloc и т.д.). В общем, линкер берёт main.o, склеивает его с системными crt*.o и библиотеками

Если .с файлов много, то используют сборщики - программа, которая вызывается, которая смотрит например все .с файлы в папке и которая инициирует компиляцию каждого таокго файла.
#### Непосредственно про php
Установка PHP в первую очередь подразумевает установку интерпретатора PHP - php.exe. Интерпретатор PHP — это бинарная программа, большая часть ядра которого (так называемый Zend Engine) написана на языке C. Логически интерпретатор php.exe можно разделить на два компонента, которые живут в одном файле, - Zend Engine и Виртуальная машина (Zend VM). Zend Engine превращает .php файл в байт‑код (opcodes). Zend VM исполняет opcodes шаг за шагом

После установки интерпретатора необходимо, если php.exe добавлен в PATH, необходимо выполнить команду `php файл.php`. Если не добавлен, то `C:\php\php.exe файл.php`
### Apache. Как связывать с PHP
Apache - это программа‑веб‑сервер, которая принимает запросы от браузера, отдаёт статику (HTML, картинки) и «связывает» браузер с динамической частью (твоими PHP‑скриптами). #### Исправление конфигурации для https
Нужно исправить текущий "C:\Apache24\conf\extra\httpd-ssl.conf". Сейчас там:
```
<VirtualHost _default_:443>
  DocumentRoot "C:/Apache24/htdocs"
  ServerName localhost:443
  ErrorLog "C:/Apache24/logs/error-ssl.log"
  TransferLog "C:/Apache24/logs/access-ssl.log"

  SSLEngine on
  SSLCertificateFile "C:/Apache24/conf/server.crt"
  SSLCertificateKeyFile "C:/Apache24/conf/server.key"

  <Directory "C:/Apache24/htdocs">
    Options Indexes FollowSymLinks
    AllowOverride None
    Require all granted
  </Directory>
</VirtualHost>       
```
Концептуально httpd-ssl.conf — файл, который настраивает Apache для работы с HTTPS‑запросами. В нём внутри <VirtualHost _default_:443> указывается:
* DocumentRoot - Указывает, какая папка на диске считается «корнем сайта».
* ServerName - Задаёт имя виртуального хоста.
* ErrorLog - Указывает файл, куда сервер будет писать ошибки для этого виртуального хоста.
* TransferLog - Указывает файл для журнала доступа (access log) этого хоста. В него записываются все запросы к сайту: IP‑адрес клиента, запрошенный URL, код ответа (200, 404, 500), размер ответа, User‑Agent и т. д.
* SSLEngine on - Включает поддержку SSL/TLS для этого VirtualHost. Без этой строки Apache не будет обрабатывать HTTPS‑запросы на этом хосте. Даже если есть сертификат и порт 443
* SSLCertificateFile - Указывает путь к SSL‑сертификату (публичная часть). Это сертификат, который браузер получает при установке соединения. Он содержит доменное имя, публичный ключ и подпись удостоверяющего центра.
* SSLCertificateKeyFile - Указывает путь к приватному ключу сертификата. Приватный ключ нужен серверу, чтобы расшифровать данные, зашифрованные браузером с помощью публичного ключа из сертификата.
* <Directory "C:/Apache24/htdocs"> … </Directory> - Открывает блок настроек, которые применяются только к указанной папке (C:/Apache24/htdocs). Всё, что внутри этого блока, действует только для файлов и подпапок в этой директории.
* Options Indexes FollowSymLinks
  * Indexes: если в папке нет index.html (или другого индексного файла), Apache покажет список файлов в этой папке.
  * FollowSymLinks: разрешает серверу переходить по символическим ссылкам (аналог ярлыков в Windows).
* AllowOverride None - Запрещает Apache читать и применять настройки из файлов .htaccess в этой папке и её подпапках. В .htaccess обычно настраивается Роутинг (если такого пути нет, то возвращаем начальную страницу, а не возвращаем ошибку), Защита папки паролем (в .htaccess можно закрыть доступ к папке паролем), Запрет доступа к файлам конфигурации (в .htaccess можно  запретить отдачу .env, config.php, composer.json файлов) и ещё пару вещей.
* Require all granted - Разрешает доступ всем к этой папке.
Меняем:
```
<VirtualHost _default_:443>
    DocumentRoot "C:/localhost"

```

### Отправление http-запроса с помощью php, обработка ответа, выдача ответа клиента
Более 2 часов вместе с ИИ пробовал запустить отправку GET. Но не вышло. Кратко резюмирую ход неудачи:
*  Активация нативного curl в PHP
    * Действия: Раскомментирование extension=curl в php.ini, попытка синхронизации DLL-библиотек (создание .bak, замена файлов) между папками Apache и PHP для устранения конфликта версий OpenSSL.
    * Результат: Модуль curl не загружался либо вызывал падение веб-сервера. Конфликт версий библиотек OpenSSL между сборками Apache и PHP на ОС Windows оказался неразрешимым в рамках локальной среды.
* Использование file_get_contents с отключением SSL.
    * Действия: Использование stream_context_create с флагами verify_peer => false.
    * Результат: Ошибка Failed to open stream: No such file or directory.
    * Причина: Из-за конфликта библиотек настройка игнорировалась, соединение рвалось на этапе TLS-рукопожатия.

Вывод: Локальная среда разработки (Windows + Apache + PHP) оказалась непригодной для выполнения HTTPS-запросов к серверу с самоподписанным сертификатом из-за фундаментальной несовместимости библиотек OpenSSL в сборке.
